# ADR-0002: Manual Lazy Dependency Injection (`AppGraph`)

- **Status:** Accepted
- **Date:** 2026-11-27

## Context

LockedSecure needs explicit constructor injection so every feature (`powerblocker`, `deviceadmin`, `dashboard`) can be tested in isolation and replaced behind domain interfaces without touching Android entry points.

## Options Considered

1. **Dagger / Hilt:** Compile-time graph validation, but requires KSP/annotation processing, Hilt Gradle plugin, `androidx.appcompat`/`fragment` transitive graph overhead, and generated bytecode for only 4 collaborators.
2. **Koin:** Service-locator DSL with runtime reflection/module registration overhead and extra runtime library size (~150+ KB).
3. **Manual lazy composition root (`AppGraph`):** Pure Kotlin class (~75 lines) held lazily by `LockedSecureApp`, constructing each feature's collaborators lazily on first access.

## Decision

Use **manual lazy constructor DI** via `com.example.lockedsecure.app.AppGraph`.

## Consequences

- **Zero runtime library cost** (0 KB added dependencies, 0 reflection, 0 annotation processors).
- **Zero startup penalty:** `PowerMenuBlockerService` only allocates `PowerMenuActionPolicy`; `AdminReceiver` only allocates `UninstallProtectionUseCase`; `MainActivity` gets a per-Activity `DashboardController` without retaining an Activity reference in `AppGraph`.
- **Trivial to understand and replace:** Any contributor can read the entire object graph in one 75-line file (`AppGraph.kt`).
- **Acyclic dependency direction:** `AppGraph` references manifest components by class-name constants so `com.example.lockedsecure.app` never imports `com.example.lockedsecure` entry points (verified automatically by `ArchitectureBoundaryTest`).
